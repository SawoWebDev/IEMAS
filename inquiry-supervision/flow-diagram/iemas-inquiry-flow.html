How an inquiry email moves through IEMAS

From the moment a customer's email lands in an agent's mailbox to the moment the inquiry is marked resolved. Each step shows whether AI runs there or plain code does, and what the live simulation proved. The live-run evidence is from 2026-11-17 and is kept as history; later changes are marked.

Colour key

AI (LLM call) System / code (deterministic, scheduled job) External (email / SMTP) Human (employee: Windows Agent app, Outlook, CMS)

"Agents" in IEMAS are the human employees using the Windows Agent desktop app. There are no AI sub-agents: the system is a pipeline of scheduled Hangfire jobs in the iemas-inq-api container, and only two of them call an LLM.

Supervision & Escalation

  • Deadlines and reminders (background jobs)
  • Business calendar: weekends, holidays from setting inquiry.holidays, DST-safe time zone
  • Escalation levels: supervisor, department manager, group, with recipient fallback
  • One escalation per case + level
  • SMTP failures retried after 5 / 15 / 60 min, max 3, and cancelled once the case is resolved

Monitoring & Reliability

  • GET /api/v1/system-health/jobs: last success, last failure, duration, retries, pending
  • Healthy / Stale / Failing feeds the health check; CMS System Health "Scheduled jobs" table
  • OpenRouter: timeout, bounded retries with backoff honouring Retry-After, fallback models, JSON validation with one repair call, circuit breaker
  • AI failure = keep supervising

Security & Audit

  • Every AI call audited: model, model version, prompt version, decision, confidence, explanation, attempts, failure category, cost (GET /api/v1/ai-usage/audit)
  • Resolution confirm/reject and classification reviews audited
  • Authorization matrix test over all controllers
  • Agent replies encrypted with AES-GCM
  • Per-account login lockout

Key Benefits

  • No lost emails or messages
  • Accurate classification
  • Reliable resolution
  • Full traceability

A customer follow-up re-enters at the top, joins the same case (CustomerFollowUpReceived) and restarts the agent's timer. Customer silence alone is never escalated. The AI can only suggest "resolved"; a person always closes the inquiry, and the ResolutionGuard can downgrade the AI's suggestion before it reaches the agent.

Step by step

a

Customer email arrives

Mail

The customer sends an email over SMTP into the agent's IMAP mailbox. In the test this was the GreenMail test mail server.

Proved by
6 hand-written emails delivered (spa hotel, heater fault, dealer, newsletter, internal logistics, "Great to meet you in Lyon")
b

email-intake

Codeevery 1 min

Fetches new mail over IMAP and writes an email_messages row. Duplicates are skipped by Message-ID and a content fingerprint (see Idempotency below). If the email belongs to an existing inquiry thread (thread id, In-Reply-To, References via ConversationThreadMatcher), it is linked straight to that case and skips screening; the assigned agent is notified.

Proved by
Henrik's follow-up joined his existing case CASE-000037 (live run). Thread follow-up behaviour is also covered by ThreadFollowUpTests.
c

email-classification filter

Code, no AIevery 1 min

ZettelkastenFilter (DeterministicEmailFilter v2) scores weighted signals:

  • inquiry phrases, product terms, request cues, dealer phrases
  • not-inquiry phrases, automated sender, internal domain sawo.com
  • sender history

Result: Inquiry (score ≥ threshold, no negatives), NotInquiry, or Uncertain.

Proved by
All 6 emails classified as expected (see table below)
d

AI classifier, only for Uncertain emails

AI

EmailClassificationService → OpenRouterClassificationProvider. Model qwen/qwen3-30b-a3b-instruct-2507, fallback mistralai/mistral-small-3.2-24b-instruct. Returns relevance, category, priority and confidence. ClassificationDecisionPolicy (plain code) turns that into Important, NotImportant or ReviewRequired. If every model fails, the email goes to ReviewRequired and is never silently dropped. Calls go through the reliability layer: timeout, bounded retries with backoff (honouring Retry-After), fallback models, JSON validation with one repair call, circuit breaker. Every call is written to the AI audit log.

Writes
email_classifications, ai_usage_records (with audit fields)
Proved by
"Great to meet you in Lyon": filter 0 → Uncertain → AI 0.95 → NotImportant, no case. Cost $0.00018 (live run). Reliability and audit are covered by Ai/OpenRouterReliabilityTests and Ai/AiAuditTests.
e

Manual review queue (ReviewRequired)

Person

Emails the AI could not decide (ReviewRequired) or that hit an AI failure wait in the CMS Email Classification page. A supervisor or above works the queue through /api/v1/classification-reviews: approve (creates the case), reject (no case) or correct the classification. Each review is audited. This branch previously had no workflow.

Proved by

f

case-workflow

Codeevery 1 min

CaseWorkflowService + CaseMatchingService create a new case or join an existing one (thread id, In-Reply-To, References, participants). The owner is the mailbox's OwnerEmployee. NotificationService pushes a "New Email" pop-up to the Windows Agent over SignalR. Notifications are unique per case + email + type, so a re-run never double-notifies.

Proved by
CASE-000036/37/38 created with the right owners. Each agent's sync showed only their own cases.
g

Agent replies from Outlook

Person

The reply goes over SMTP to the customer, and a copy lands in the agent's Sent folder.

Tested
Through the protocol only. The real Windows Agent GUI was not driven.
h

conversation-sync

Codeevery 5 min + event-triggered

ConversationSyncService reads the Sent folder over IMAP. It stores outbound messages linked by thread headers as role Agent (to the customer) or Internal (only to @sawo.com). Agent reply bodies are encrypted (AES-GCM). InquiryLifecycle moves the stage.

  • Event-triggered: a sync of the case's mailbox also runs immediately when the agent confirms or rejects resolution and on other agent case actions, so the last reply is stored before the AI or the agent decides.
  • Grace window: Resolved cases keep being synced for 1 day.
Proved by
Dealer thread: internal forward and export's reply stored as Internal (live run). ConversationSyncOnConfirmTests covers the sync-on-confirm fix.
Was a bug
FIXED: the old job skipped Resolved cases, so a reply sent just before confirmation was lost (see Known gaps for the history)
i

AI resolution assessment

AIwhen the conversation changes

ResolutionAssessmentService → OpenRouterResolutionAssessor, Qwen3-30B with a fallback chain and the same reliability layer as the classifier. Verdict: AcknowledgedOnly, InProgress, CustomerWaiting or AppearsResolved, plus confidence, reason and a list of open items. AppearsResolved with confidence ≥ 75% that also passes the ResolutionGuard moves the stage to PotentiallyResolved and asks the agent to confirm. The AI never closes an inquiry. If the AI fails, supervision simply continues.

Proved by
6 checks, $0.00053 total (live run). Acknowledgement → AcknowledgedOnly. Customer thanks → AppearsResolved. Megan's reply → InProgress.
Not yet
The new prompts have not been validated against a live model
j

ResolutionGuard

Code, no AI

Deterministic check after the AI verdict. It downgrades AppearsResolved (the case stays open and supervised) when any of these holds:

  • the customer only says thanks without confirming the problem is solved
  • the agent spoke last
  • the customer's last message asks a question or reports a problem
  • the agent's last message ends with a question, asks for approval, or promises later action or a pending quotation
  • the AI itself listed open items
Proved by
Ai/ResolutionGuardTests (automated)
k

inquiry-supervision timers

Codeevery 1 min

InquirySupervisionService + SupervisionRules + BusinessCalendar. The calendar covers business hours, weekends, holidays from the setting inquiry.holidays, and a DST-safe time zone.

  • First reply due within 4 business hours
  • Reminder every 2 hours, 2 reminders, then escalation
  • Idle limit 1 business day
  • Customer wait limit 3 calendar days
  • Resolution target 5 business days
Proved by
Megan's case: 2 reminders, then escalation, then no second escalation after agent2 replied (live run). BusinessCalendarHardeningTests and SupervisionHardeningRulesTests cover the later rules.
l

Escalation email

CodeSMTP

EscalationService picks recipients from the policy level (supervisor → department manager → group), with a fallback when a level has no recipient. EscalationEmailComposer builds the email, and SmtpEscalationEmailSender sends it through the oldest active Outbound SMTP account. An EscalationEvent row is written and the agent gets an "Escalated" pop-up. Level 2 follows one business day later. Only one escalation exists per case + level. A failed SMTP send is retried after 5, 15 and 60 minutes (max 3 attempts) and cancelled once the case is resolved.

Proved by
Escalation email delivered at 00:03 UTC, 10 test-minutes after Megan wrote (live run). It listed customer, subject, agent, status, replied = No, inactivity, both reminders, the reason and a CMS link. Retry rules: EscalationReliabilityTests.
m

Agent confirms or rejects

Person

In the Windows Agent ("Confirm Resolved", case-actions actionType 10; RejectResolution = 11) or the CMS. Confirm sets the stage to Resolved and supervision stops. Reject sends the case back to supervision. Both actions are audited and trigger a conversation sync first.

Proved by
agent1 confirmed Henrik's case → Resolved. agent2 trying to confirm agent1's case → HTTP 400. (live run)
n

Idempotency

Code

Re-running a job never duplicates work. Inbound and synced messages are deduplicated by Message-ID plus a content fingerprint. Notifications are unique per case + email + type. The same rule applies to escalations (one per case + level).

Proved by
IdempotencyTests (automated)
Limit
Message-ID dedupe is enforced in the application only, not by a database unique index

Known gaps

FIXED: the agent's last reply could go missing from the record

Found by the live run on 2026-11-17. conversation-sync ran only every 5 minutes and skipped Resolved cases. If the agent confirmed before the next sync, their last reply was never stored, and the AI judged "resolved" without seeing it. The timeline below is kept as history.

23:57:07Agent1 sends the full proposal to Henrik 23:57:09Henrik replies "thanks" 23:58AI judges AppearsResolved, without the proposal 23:59:20Agent1 confirms → Resolved 00:00Then (old behaviour): sync skipped the now-Resolved case. Proposal never stored.

Stored conversation at the time: Customer, Agent, Customer, Customer. Fix: the case's mailbox is synced when the agent confirms or rejects (and on other agent actions), and Resolved cases keep syncing for a 1-day grace window. Covered by ConversationSyncOnConfirmTests; a live re-run is still needed to confirm it end to end.

Mitigated: AI may say "resolved" too early

The deterministic ResolutionGuard now downgrades AppearsResolved in the cases that caused this (agent spoke last, agent asked a question or promised later action, customer asked a question, thanks only, open items). The 75% threshold stays. The new prompts are not yet validated live.

Resolved: ReviewRequired branch

ReviewRequired and AI-failure emails now go to a manual review queue (CMS Email Classification, /api/v1/classification-reviews, supervisor and above). Not yet exercised in a live run.

Remaining gaps

Data protection and access

  • Inbound customer bodies are stored unencrypted. Only agent replies are encrypted.
  • No department scoping for supervisors: a supervisor can act on cases outside their department.

Database constraints

  • Message-ID dedupe is application-level only. There is no DB unique index, and existing data may already contain duplicates.
  • The escalation unique index (case + level) is created only if the existing data has no duplicates.

Monitoring and metrics

  • Job-monitoring history is in memory and is lost on restart.
  • Analytics uses wall-clock time, not business hours.

Validation still owed

  • The new prompts have not been validated against a live model.
  • The Windows Agent GUI is still untested by automation.
  • A live re-run of live_simulation.py is needed.
